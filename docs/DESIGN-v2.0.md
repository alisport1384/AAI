## 1. تعریف محصول

**هوشیار** یک موتور مستقل است که «کالا» را می‌فهمد: مشخصات را از منابع مختلف (فهرست خود اپ، صفحهٔ محصول، تصویر، اسکرین‌شات) استخراج می‌کند، کالاهای هم‌ارز را یکسان‌سازی می‌کند، قیمت را نرمال می‌کند، امتیاز ارزش می‌دهد و به پرسش‌های کاربر **با استناد** پاسخ می‌دهد — همهٔ این‌ها بدون ارسال حتی یک بایت به سرویس بیرونی.

### 1.1 سه حالت اتصال به «اپ انتخابی»

| حالت | مکانیزم | عمق داده | نیاز به همکاری اپ میزبان |
|---|---|---|---|
| **M1 — Embedded** | AAR/SDK داخل اپ میزبان؛ دسترسی مستقیم به فهرست و رویدادها | کامل (DB اپ) | لازم (یکپارچه‌سازی) |
| **M2 — Import** | ورود داده با فایل (CSV/JSON/DB) یا پایپ‌لاین محلی اپراتور | بالا، دسته‌ای | ندارد |
| **M3 — Screen-Assist** | خواندن صفحهٔ هر اپی که کاربر انتخاب می‌کند: درخت Accessibility + اسکرین‌شات (MediaProjection) → VLM/OCR | متوسط، لحظه‌ای | ندارد |

در M3، «هر اپ انتخابی» واقعاً هر اپی است: کاربر اپ را انتخاب می‌کند، هوشیار صفحه را می‌خواند، کالا را می‌شناسد و به پرسش‌ها جواب می‌دهد. **هوشیار خودش در آن اپ عملیات خرید انجام نمی‌دهد؛ تحلیل و پاسخ می‌دهد و ناوبری را پیشنهاد می‌کند** (تأیید گام‌به‌گام برای هر لمس، §15).

### 1.2 کارهای هستهٔ محصول

1. استخراج مشخصات از عنوان/توضیح/جدول/تصویر.
2. یکسان‌سازی کالا در منابع مختلف (همان گوشی با سه عنوان متفاوت).
3. نرمال‌سازی و تاریخ‌گذاری قیمت؛ تشخیص قیمت پرت.
4. مقایسهٔ چند کالا و امتیاز «ارزش» بر پایهٔ Market Pack.
5. پاسخ به پرسش‌های بازار با شاهد و امتناع صریح در نبود شاهد.
6. یادگیری ترجیح کاربر و حفظ آن بین نشست‌ها.

## 3. قیدهای بنیادین و راه‌حل آن‌ها

### 3.1 «بدون Google Play»
سیاست Play حذف می‌شود، اما **قیدهای سیستم‌عامل حذف نمی‌شوند**: Accessibility همچنان باید توسط کاربر روشن شود، `MANAGE_EXTERNAL_STORAGE` همچنان «دسترسی ویژه» می‌خواهد، و `/data/data/<app>` هرگز بدون root خواندنی نیست. آنچه اضافه می‌شود: امکان **OTA خودی**، بارگذاری ماژول، Shizuku/Device Owner.

### 3.2 «هیچ API یا توکن از جای دیگر»
| نیاز | راه‌حل بدون API | هزینه |
|---|---|---|
| استنتاج زبانی | llama.cpp + GGUF روی دستگاه | صفر |
| بردار معنایی | EmbeddingGemma-300M محلی | صفر |
| تشخیص متن تصویر | Tesseract (`fas`/`eng`) + VLM محلی | صفر |
| جست‌وجوی وب | آداپترهای HTML + خزش دامنه‌های بازار + ایندکس FTS5 محلی | صفر ریالی؛ فقط ترافیک |
| تحلیل تصویر محصول | Qwen3-VL-2B (ردهٔ C) | صفر |
| تلمتری/کرش‌ریپورت | لاگ محلی + خروجی دستی کاربر | صفر |

**صداقت مهندسی:** هیچ راهی برای داشتن «ایندکس وب در سطح گوگل» بدون API یا خزش وجود ندارد. پس معماری، وابستگی به موتور عمومی را **کمینه و قابل‌جایگزین** می‌کند: اولویت با جست‌وجوی مستقیم داخل خود بازارها و ایندکس محلی است؛ موتور عمومی آخرین حلقه است (§12.2).

### 3.3 «بازار خاص»
همه‌چیزِ دامنه در **Market Pack** بیرون از کد قرار می‌گیرد (§6) تا موتور ثابت بماند و بازار قابل تعویض باشد.

### 3.4 «خودش را اصلاح کند»
سه سطح با اختیارات صریح: مهارت اعلانی، اسکریپت سندباکس‌شده، افزونهٔ بومی امضاشده (فقط انسانی). کد تولیدشده توسط مدل **هرگز** به سطح سوم راه نمی‌یابد (§14).

### 5.1 چهار جریان اصلی

```
[J1] تحلیل کالا
ورودی (متن/عکس/اسکرین‌شات/لینک) → استخراج ویژگی → Resolver (کالای کانونی)
 → جمع شواهد (فهرست اپ، خزش، حافظه) → نرمال‌سازی قیمت
 → امتیاز ارزش + پرچم‌های هشدار → کارت تحلیل با استناد

[J2] پرسش‌وپاسخ
پرسش → تشخیص نیت (تاکسونومی پک) → بازیابی شواهد هدفمند
 → ساخت پاسخ با گرامر → Critic (شاهد دارد؟ تناقض؟) → پاسخ + منابع / امتناع

[J3] همگام‌سازی داده
کار دوره‌ای → SourceSync (فهرست اپ / خزش) → Extract → Normalize
 → Match/Dedupe → Upsert + PricePoint → به‌روزرسانی ایندکس

[J4] خودافزایی
شکست مکرر/الگوی موفق → پیشنهاد مهارت یا اسکریپت → اعتبارسنجی ایستا
 → Dry-run → EvalGate → تأیید کاربر → فعال‌سازی نسخه‌دار
```

## 7. لایهٔ داده

```sql
PRAGMA journal_mode=WAL; PRAGMA foreign_keys=ON; PRAGMA busy_timeout=5000;

-- کالای کانونی
CREATE TABLE product (
  id TEXT PRIMARY KEY, pack_id TEXT NOT NULL, category TEXT NOT NULL,
  brand TEXT, family TEXT, model TEXT,
  canonical_name TEXT NOT NULL, canonical_norm TEXT NOT NULL,
  attrs_json TEXT NOT NULL DEFAULT '{}',   -- {id: {value, unit, conf, src}}
  attr_hash TEXT NOT NULL,                 -- برای کشف تکرار
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL
);
CREATE INDEX idx_product_key ON product(pack_id, brand, family, model);
CREATE UNIQUE INDEX idx_product_attr ON product(pack_id, attr_hash)
  WHERE attr_hash IS NOT NULL AND attr_hash <> '';   -- کالای ناقص مشمول یکتایی نیست

-- آگهی/عرضه (چند منبع برای یک کالا)
CREATE TABLE listing (
  id TEXT PRIMARY KEY, product_id TEXT REFERENCES product(id) ON DELETE SET NULL,
  source_id TEXT NOT NULL, source_url TEXT, seller TEXT, city TEXT,
  title_raw TEXT NOT NULL, price_irt INTEGER, condition TEXT,
  stock INTEGER, warranty TEXT, raw_json TEXT, image_uris TEXT,
  first_seen INTEGER NOT NULL, last_seen INTEGER NOT NULL,
  trust_score REAL NOT NULL DEFAULT 0.5
);
CREATE INDEX idx_listing_product ON listing(product_id);
CREATE INDEX idx_listing_source  ON listing(source_id, last_seen DESC);

-- سری زمانی قیمت
CREATE TABLE price_point (
  product_id TEXT NOT NULL, at INTEGER NOT NULL, price_irt INTEGER NOT NULL,
  source_id TEXT NOT NULL, listing_id TEXT NOT NULL,
  PRIMARY KEY (product_id, at, listing_id)          -- دو آگهی هم‌منبع در یک لحظه تداخل نمی‌کنند
);
CREATE INDEX idx_price_recent ON price_point(product_id, at DESC);

-- سند منبع (صفحه/فایل/تصویر) برای استناد
CREATE TABLE source_doc (
  id TEXT PRIMARY KEY, kind TEXT NOT NULL CHECK(kind IN ('page','file','image','screen','pack','listing')),
  uri TEXT, sha256 TEXT, fetched_at INTEGER, lang TEXT, text TEXT,
  meta_json TEXT, ttl INTEGER
);
CREATE TABLE claim (              -- اتصال ادعا به شاهد
  id INTEGER PRIMARY KEY, subject_kind TEXT, subject_id TEXT,
  attr TEXT, value TEXT, source_doc_id TEXT REFERENCES source_doc(id),
  span TEXT, confidence REAL, created_at INTEGER
);

-- حافظهٔ کاربر و دانش
CREATE TABLE memory_item (
  id TEXT PRIMARY KEY, kind TEXT NOT NULL CHECK(kind IN ('preference','fact','episode','note')),
  lang TEXT NOT NULL, title TEXT, body TEXT NOT NULL, body_norm TEXT NOT NULL,
```

## 8. استخراج و یکسان‌سازی

### 8.1 نرمال‌سازی فارسی/انگلیسی (نسخهٔ نمایش حفظ می‌شود)

| قاعده | نمونه | کاربرد |
|---|---|---|
| NFC | «ﻛﺘﺎﺏ» → «کتاب» | همه‌جا |
| `ك→ک`, `ي→ی`, `ة→ه` | «كتاب» ≡ «کتاب» | فقط ایندکس/تطبیق |
| اعداد `۰-۹`/`٠-٩` → ASCII؛ `٫→.`؛ حذف `٬` | «۲۵٬۰۰۰» → «25000» | قیمت و مشخصه |
| حذف اعراب و تطویل | «کِتاب» → «کتاب» | جست‌وجو |
| نیم‌فاصله دو-نسخه‌ای | «می‌روم» ≡ «میروم» | جست‌وجو |
| یکسان‌سازی واحد | «۱۲۸ گیگ» → `storage_gb=128` | ویژگی عددی |
| واژه‌نامهٔ برند فارسی | «سامسونگ» → `Samsung` | Resolver |

### 8.2 یکسان‌سازی کالا (Entity Resolution)

```
1 Blocking: (pack_id, brand, family) → نامزدها
2 توکنیزه: مدل، حافظه، رم، نسخه (Pro/Plus/Ultra) با واژه‌نامهٔ پک
3 امتیاز تطبیق:
   s = 0.5·Jaccard(tokens) + 0.3·cos(vec_text) + 0.2·(1 − |Δattr|/max)
4 آستانه: s ≥ 0.82 → ادغام؛ 0.60 ≤ s < 0.82 → صف «نیازمند تأیید» در UI؛ s < 0.60 → کالای جدید
5 تضاد ویژگی: اگر ≥2 ویژگی عددی اختلاف > 20% داشته باشند → ادغام رد می‌شود (کالای متفاوت)
```
هر ادغام در `audit_log` ثبت و از UI قابل تفکیک است («چرا این دو یکی هستند؟»).

### 8.3 استخراج ویژگی — ترتیب اولویت
1. **JSON-LD / دادهٔ ساختاریافته** صفحه (ارزان، دقیق).
2. **جدول مشخصات** (پارسر جدول + نگاشت به واژه‌نامهٔ پک).
3. **متن آزاد** (regex عددی + واحد + واژه‌نامه؛ «۱۲۸/۸» → ram/storage).
4. **VLM** فقط اگر سه مسیر بالا ناقص بمانند: تصویر محصول/اسکرین‌شات → JSON با گرامر.
5. **OCR فارسی** (Tesseract `fas`) برای تصویر متنی؛ VLM به‌عنوان داور در تضاد.

هر ویژگی سه چیز حمل می‌کند: `value`، `conf`، `src` (شناسهٔ `source_doc`). ویژگی بدون منبع، **در پاسخ استفاده نمی‌شود**.

### 8.4 نرمال‌سازی قیمت

```
ورودی: "۱٫۲۵۰٫۰۰۰ تومان" | "1250000" | "۱٫۲ میلیون تومان" | "125000 ریال" | "۱۲۵۰ ت"
1 یکسان‌سازی ارقام و جداکننده‌ها
2 تشخیص ضریب: «میلیون»×1e6، «هزار»×1e3، «م»/«ملیون»×1e6
3 تشخیص ارز: ریال → ÷10 (به تومان)
4 اعتبارسنجی بازه: 1e3 ≤ price_irt ≤ 1e11  (خارج → رد و پرچم)
5 ثبت در price_point + محاسبهٔ percentile
```
**خطای رایج و کنترل آن:** «۱۲۵۰» در آگهی گوشی ≠ ۱۲۵۰ تومان؛ قاعدهٔ پک: اگر عدد < 1e5 و واحد نداشت → «نامعلوم» علامت می‌خورد و در تحلیل وزن نمی‌گیرد (نه اینکه حدس زده شود).

## 9. موتور تحلیل

### 9.1 امتیاز ارزش

```
S_attr = Σ (w_i · sim(attr_i, ideal_i)) / Σ w_i        # sim: عددی → خطی نرمال‌شده؛ شمارشی → بولی
P      = percentile(price_irt | window=30d, same product)
S      = 0.6·S_attr + 0.4·(1 − P)
verdict (آستانه‌های موتور): S ≥ 0.70 → «ارزش بالا» | 0.45 ≤ S < 0.70 → «متوسط» | S < 0.45 → «گران»
برچسب قیمتی (آستانه‌های پک، مستقل از verdict):
  P ≤ bands.good → «ارزان» | bands.good < P ≤ bands.fair → «متعارف»
  bands.fair < P ≤ bands.high → «بالا» | P > bands.high → «پرت»
```
دو آستانهٔ جدا از هم عمداً نگه داشته می‌شوند: verdict کیفیتِ «کالا در برابر قیمت» را می‌سنجد، برچسب قیمتی فقط جایگاه قیمت در توزیع است. پک می‌تواند `bands` را تغییر دهد ولی آستانه‌های verdict متعلق به موتورند (برای مقایسه‌پذیری بین پک‌ها).
خروجی همیشه همراه با: تعداد منابع، بازهٔ قیمت، و «چه چیزی را نتوانستم بررسی کنم» (شفافیت نقص داده).

### 9.2 مقایسه
جدول ویژگی‌های مشترک + تفاوت‌ها، «برنده» به‌ازای هر ویژگی، و جمع‌بندی مشروط به ترجیح کاربر (`preference` در حافظه: مثلاً «باتری برایم مهم‌تر از دوربین است») با وزن‌دهی مجدد پویا.

### 9.3 پرچم‌های هشدار
`price_too_low`، `spec_conflict`، `duplicate_listing` (SimHash عنوان + dHash تصویر)، `photo_mismatch` (VLM: تصویر با مدل نمی‌خواند)، `seller_unstable` (نرخ ناپدیدشدن آگهی). **همه با زبان احتمالی و ارجاع به شاهد؛ هیچ اتهامی.**

### 9.4 سری زمانی
نمودار ۳۰/۹۰/۳۶۵ روزه با میانه و صدک‌ها؛ تشخیص پرش (> ۲۵٪ در ۷ روز) و ثبت رویداد در `audit_log`.

## 10. موتور پرسش‌وپاسخ

### 10.1 نیت‌ها (از پک) و مسیر شواهد

| نیت | شواهد لازم | اگر نبود |
|---|---|---|
| `price.check` | آخرین `listing.price_irt` + `price_point` | «قیمت به‌روز ندارم» + آخرین تاریخ |
| `price.history` | `price_point` بازه | امتناع نرم |
| `spec.lookup` | `attrs_json` با منبع | امتناع نرم |
| `compare` | دو محصول با ویژگی‌های هم‌پوشان | پرسش تکمیلی |
| `authenticity.check` | نشانه‌های اصالت (گارانتی/رجیستری/منبع) | هشدار + توصیهٔ بررسی دستی |
| `compatibility` | ویژگی‌های سازگاری پک | امتناع |
| `seller.trust` | تاریخچهٔ فروشنده در DB محلی | «دادهٔ کافی ندارم» |
| `stock.check` | `listing.stock` + `last_seen` | «وضعیت نامعلوم» |
| `risk.flag` | red_flags | — |

### 10.2 قالب پاسخ (اجباری، با گرامر)

```json
{
  "intent": "price.check",
  "answer_fa": "…",
  "bullets": ["…"],
  "citations": [ { "ref": "L:8f2a", "kind": "listing", "url": "…", "at": 1763300000 } ],
  "confidence": 0.0,
  "missing": ["تاریخ دقیق گارانتی"]
}
```
پاسخ بدون `citations` برای هر ادعای عددی/واقعی → **بازنویسی یا امتناع**.

### 10.3 Critic
پاس دوم: هر ادعا ↔ شاهد؛ تناقض بین منابع → اولویت به منبع با `trust_score` بالاتر و اعلام صریح؛ `confidence < 0.5` → جملهٔ عدم‌قطعیت.

### 10.4 امتناع
سه سطح: `soft` («در حافظه/منابع چیزی ندارم؛ می‌خواهید جست‌وجو کنم؟»)، `hard` (موضوع خارج از دامنه)، `unsafe` (توصیهٔ پزشکی/حقوقی/مالیِ قاطع). امتناع هرگز با پاسخ ساختگی جایگزین نمی‌شود.

### 11.1 رده‌ها

| رده | RAM | LLM | VLM | OCR | بافت | انتظار |
|---|---|---|---|---|---|---|
| A | 4GB | Qwen3.5-0.8B Q8 (~0.8GB) | — | Tesseract | 4096 | 25–40 tok/s |
| B | 6–8GB | Qwen3.5-2B IQ4_NL (~1.2GB) | SmolVLM2-500M اختیاری | Tesseract | 8192 | 15–25 tok/s |

قاعدهٔ سخت: حجم مدل در حافظه ≤ ۴۵٪ RAM کل؛ در غیر این‌صورت یک رده پایین.
**بدون VLM، محصول کار می‌کند**: VLM یک مسیر ارتقاست، نه پیش‌نیاز.

### 11.2 پارامترها و محافظ‌ها
`threads = max(2, cores/2)`؛ KV Q8_0 (رده A/B)؛ **prefix cache** فعال (هش system+pack+tools)؛ `temperature=0.2` برای استخراج، `0.6` برای گفتگو؛ `n_predict` ≤ 512؛ گرامر اجباری برای JSON؛ `ThermalGuard`: LIGHT→ threads−1، MODERATE→ ردهٔ پایین‌تر، SEVERE/باتری<15%→ توقف کار غیرتعاملی؛ `onTrimMemory` → آزادسازی مدل.

### 11.3 OCR و بینایی
- Tesseract با `fas+eng`، پیش‌پردازش: grayscale، deskew، binarize (adaptive)، بزرگ‌نمایی ۲× برای متن ریز، برش ناحیهٔ جدول.
- **نکتهٔ مهم:** ML Kit برای خط فارسی/عربی قابل اتکا نیست؛ مسیر اصلی Tesseract است و VLM داور.
- تصویر محصول: VLM با پرامپت JSON-محور (`{"brand","model","storage_gb","confidence"}`) و گرامر؛ نتیجهٔ VLM هرگز بدون تأیید متقابل به‌عنوان «قطعی» ثبت نمی‌شود.

## 12. Search Core بدون API

### 12.1 اجزا

```
QueryPlan (پک: کدام منابع برای کدام نیت)
  ├─ MarketSearch   → جست‌وجوی داخلی خود بازارها (پایدارترین؛ پارسر اختصاصی هر دامنه)
  ├─ LocalIndex     → FTS5 روی source_doc (هر چیزی که قبلاً دیده‌ایم)
  ├─ GeneralWeb     → آداپترهای HTML موتورها (Google/Bing/DDG/Mojeek)
  └─ DeepFetch      → واکشی صفحهٔ انتخاب‌شده + Extractor
Health/Backoff → RateLimiter(per-domain) → Robots → Cache(TTL/ETag) → CostMeter(فقط شمارش، بدون پول)
```

### 12.2 واقعیت‌های اندازه‌گیری‌شده که طراحی را قید می‌زنند

| یافته | پیامد طراحی |
|---|---|
| DuckDuckGo API رسمی ندارد؛ `html.duckduckgo.com` بعد از اولین درخواست معمولاً ۲۰۲ + چالش JS می‌دهد | آداپتر DDG «بهترین تلاش» است، نه مسیر اصلی |
| Bing Search API بازنشسته (۲۰۲۵-۰۸-۱۱) | حذف کامل از طرح |
| Google CSE برای مشتری جدید بسته و ۲۰۲۷ متوقف | حذف |
| موتورهای فارسی (Parsijoo/Yooz/Rismoon) کیفیت و پایداری پایین و وضعیت نامعلوم | اختیاری و غیرقابل‌اتکا؛ مسیر اصلی: جست‌وجوی داخلی بازارها |
| پارسر SERP عمر کوتاه دارد (چند هفته) | آداپتر نسخه‌دار + پایش سلامت + هشدار «نیازمند به‌روزرسانی پارسر» + آزمون روزانه |

### 12.3 آنچه انجام **نمی‌شود**
دور زدن CAPTCHA، چرخش پروکسی برای فرار از بلاک، تغییر هویت مرورگر برای فریب، اسکرپ انبوه. سیاست: نرخ ≤ ۱ درخواست/۲ ثانیه به هر دامنه، احترام به `robots.txt`، `User-Agent` صادق، توقف فوری در ۴۰۳/۴۲۹ و علامت‌گذاری منبع به‌عنوان «غیرفعال».
> دلیل: این‌ها هم شکننده‌اند و هم ریسک حقوقی دارند (نقض شرایط استفاده قرارداد است، نه فقط فنی؛ پروندهٔ hiQ v. LinkedIn صرفاً دربارهٔ CFAA است).

### 12.4 پرکردن شکاف بدون API: چهار منبع
1. **فهرست خود اپ** (M1/M2) — دقیق‌ترین.
2. **جست‌وجوی داخلی بازارها** با پارسر دامنه‌ای.
3. **بستهٔ دادهٔ اپراتور** (`data.hpack`): امضاشده، نسخه‌دار، ورود از فایل — شامل فهرست دامنه‌های مجاز، نگاشت ویژگی، و snapshot مشخصات.
4. **خزش زمان‌بندی‌شده** روی `source_registry` (پیش‌فرض: خاموش تا کاربر روشن کند).

## 13. حافظه و یادگیری

| لایه | محتوا | جدول | عمر |
|---|---|---|---|
| L1 کاری | بافت نشست، کالای فعال | RAM | نوبت |
| L2 رویدادی | پرسش‌ها، تحلیل‌ها، نتیجه | `memory_item(kind=episode)` | هفته–ماه |
| L3 معنایی | ترجیح کاربر، واقعیت بازار، عادت‌ها | `memory_item`, `claim` | ماه–سال |
| L4 روندی | مهارت‌ها و اسکریپت‌ها | `extension` | پایدار |

**تحکیم شبانه** (WorkManager، قید شارژ+بیکاری): ادغام تکرار (SimHash64، همینگ ≤ 6)، خوشه‌بندی افزایشی، خلاصهٔ خوشه، کشف تناقض، به‌روزرسانی اهمیت، فراموشی تدریجی `R = exp(−Δt/(S·86400))` با آرشیو سرد (حذف قطعی فقط با دستور کاربر).

**ترجیح کاربر** (مثال واقعی برای این محصول): «قیمت مهم‌تر است یا اصالت؟» → وزن‌های `ideal_profile` را برای همان کاربر تغییر می‌دهد؛ در UI قابل مشاهده و بازنشانی.

## 14. خودافزایی (سه سطح)

| سطح | چیست | چه کسی می‌سازد | سطح دسترسی | تأیید |
|---|---|---|---|---|
| **E0 — مهارت اعلانی** | JSON: ترکیب ابزارهای مجاز | مدل یا کاربر | فقط ابزارهای فهرست‌شده | خودکار پس از EvalGate |
| **E1 — اسکریپت** | JS در QuickJS: منطق پارس/تبدیل داده | مدل | بدون شبکه/فایل؛ فقط ورودی/خروجی | EvalGate + تأیید کاربر |
| **E2 — افزونهٔ بومی** | AAR/DEX امضاشده | **فقط انسان** | کامل | امضا + نصب دستی |

### 14.1 سندباکس E1 (قواعد سخت)
- بدون `fetch`/`XMLHttpRequest`/WebSocket؛ شبکه فقط از طریق ابزارهای اعلانی و با مجوز.
- بدون فایل/DB مستقیم؛ فقط `input` و `return`.
- سقف: ۵۰ms×۱۰⁴ زمان CPU، ۳۲MB حافظه، بدون بازگشت/حلقهٔ بی‌پایان (شمارندهٔ گام)، قطع در timeout.
- بدون `eval` تودرتو، بدون reflection، بدون دیدن متغیرهای میزبان.
- کد باید **قطعی** باشد (بدون `Date.now`/`Math.random` در مسیر تصمیم — برای بازتولیدپذیری ارزیابی).
- هر اجرا در Go-routine/Isolate جداگانه و با `kill` اجباری.

### 14.2 خط تولید ارتقا

```
کشف (شکست مکرر پارسر، الگوی موفق، درخواست کاربر)
 → پیش‌نویس (JSON/JS با گرامر)
 → اعتبارسنجی ایستا (طرح‌واره، قابلیت‌های مجاز، سقف‌ها، ممنوعیت I/O)
 → Dry-run روی ۵۰ نمونهٔ تاریخی
 → EvalGate: مجموعهٔ طلایی پک → شرط: پیشرفت ≥ ۳٪ و صفر رگرسیون در هیچ زیرمجموعه
 → تأیید کاربر («این مهارت ساخته شد؛ فعال کنم؟» + نمایش کد/گام‌ها)
 → فعال‌سازی نسخه‌دار + ثبت در audit
 → پایش (success/latency) → افت → quarantine خودکار + rollback به والد
```

### 14.3 «بهبود برنامه‌نویسی خودش» به‌طور مشخص
- کتابخانهٔ الگو: هر پارسر موفق (مثلاً «جدول مشخصات با ستون‌های نام/مقدار») به‌عنوان قالب قابل‌استفادهٔ مجدد ذخیره می‌شود.
- تولید پارسر جدید فقط E1 است؛ E2 ممنوع.
- کیفیت کد با EvalGate سنجیده می‌شود، نه با ادعای مدل.
- **Kill switch:** یک فایل/کلید که همهٔ افزونه‌های غیرامضاشده را در ۱ ثانیه غیرفعال می‌کند.

## 17. امنیت و حریم خصوصی

| دارایی | تهدید | کنترل |
|---|---|---|
| دادهٔ بازار | استخراج/نشت | SQLCipher، کلید در Keystore، قفل بیومتریک اختیاری، `allowBackup=false` |
| اسکریپت خودساخته | فرار از سندباکس | QuickJS مجزا، بدون I/O، سقف منبع، kill switch، EvalGate |
| صفحهٔ خوانده‌شده از اپ دیگر | سوءاستفاده | فقط با اقدام کاربر، نشانگر دائمی روی صفحه، بدون ذخیرهٔ پیش‌فرض تصاویر |
| مدل/پک | دستکاری | امضا + SHA-256 + زنجیرهٔ نسخه |
| متن وب | تزریق دستور | برچسب `trust=untrusted`، بسته‌بندی `<data>`، ممنوعیت تغییر سیاست/مجوز از داده، حذف الگوهای فرمان |
| شبکه | SSRF | فقط http/https، مسدودسازی `localhost`/`127/8`/`169.254`/`10/8`/`172.16-31`/`192.168/16`، بدون `file://` |
| حساب | افشای داده | بدون تلمتری؛ خروجی گزارش فقط با اقدام کاربر |

**اصل:** دادهٔ خوانده‌شده از هر اپ دیگر یا وب، «داده» است نه «دستور»؛ هیچ داده‌ای نمی‌تواند مجوز بگیرد، افزونه بسازد یا حافظه را پاک کند.

## 18. تجربهٔ کاربری

- **کارت تحلیل کالا:** عنوان کانونی، ویژگی‌های کلیدی با نشان منبع، قیمت + صدک، verdict، پرچم‌ها، «چه چیزی نامعلوم است».
- **جدول مقایسه:** سطر ویژگی، ستون کالا، تفاوت‌ها برجسته، برنده به‌ازای ویژگی.
- **پاسخ‌ها:** هر عدد یک نشان منبع دارد؛ کلیک → سند/آگهی/تصویر.
- **RTL کامل:** Vazirmatn، `LocalLayoutDirection=Rtl`، ایزولهٔ یونیکد برای کد/لاتین، اعداد فارسی در نمایش و ASCII در محاسبه.
- **شفافیت:** نشان «تحلیل محلی» روی هر کارت؛ صفحهٔ «چه ذخیره کرده‌ام»؛ «چرا این را گفتم؟» برای هر پاسخ.
- **حالت کم‌توان:** بدون VLM، بدون خزش، فقط DB محلی + LLM کوچک.
